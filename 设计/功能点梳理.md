## 一、通用约定

### 1.1 接口链路

- `server.servlet.context-path=/api` + `kanban.api.prefix=/v1`，`WebConfig` 统一加前缀，真实路径 **`/api/v1/**`**。
- 前端 `axios` 的 `baseURL=/api`，89 处调用手写 `/v1/...`；dev 由 Vite proxy 转发到 `localhost:8080`。
- 同源 Session 认证，走 Cookie；未使用 JWT / Sa-Token。

### 1.2 响应与错误码

```text
成功：{ "code": 200, "msg": "ok", "data": ... }
失败：{ "code": 400|403|404|500, "msg": "用户可读提示", "data": null }
```

- 成功码是 **200**（`api.md` 写的 `code:0` 已过期）。
- 失败时 HTTP 状态可能仍为 200，前端只认 `body.code`。
- 无业务段位码，统一复用 HTTP 语义：

| 场景 | code |
|---|---|
| `@Valid` / `BindException` 校验失败 | 400（多字段用 `; ` 拼接） |
| 缺 `@RequestParam` | 400 |
| 参数类型不匹配（UUID 非法等） | 400 |
| 请求体 JSON 解析失败 | 400 |
| 数据完整性（超长/唯一键冲突） | 400 |
| 业务异常 `BaseException` | 自带 400/403/404 |
| 未知异常 | 500（通用文案，不泄露堆栈） |

- 前端拦截器：`code !== 200` → 提示并抛 `ApiError`；`401` → 清凭证和缓存、跳 `/login`；`403` → 只提示，**不跳登录页**。

### 1.3 鉴权链路（四道拦截器）

| 拦截器 | 范围 | 规则 |
|---|---|---|
| `UserContextInterceptor` | `/**` | 注入 `UserContext`；放行 swagger、actuator、`/error`、favicon、`/v1/users/login` |
| `ProjectPermissionInterceptor` | `/v1/**` | 按路径解析 `projectId` + 方法级权限判定；放行 `/v1/auth/**`、`/v1/users/**`、`/v1/projects`（列表/创建）、`/v1/upload/**` |
| `AdminAuthInterceptor` | `/v1/**` | 仅校验标注 `@RequireAdmin` 的接口 |
| `UploadsAuthInterceptor` | `/uploads/**` | 附件按所属项目 `issue:view` 校验，防直链越权 |

- 超管：种子 admin 固定 UUID 或 `sys_user.is_admin=true`，直接拥有 `Permission.allCodes()`。
- 权限缓存 `ConcurrentMapCache`，键 `userId:projectId`，改成员/角色时主动 evict（无 TTL）。

### 1.4 分页、排序与上传

- 统一 `PageResult { list, total }`；前端列表默认 `size=25`，树形/看板传 `size=1000` 全量。
- 排序白名单：`updatedAt/priority/severity/statusId/sortKey/createdAt`，仅 `asc|desc`。
- 上传：`POST /v1/upload/image`，单文件 5MB，落盘 `kanban.upload.dir`，经 `/uploads/**` 访问（需登录 + 项目权限）；前端支持 Ctrl+V 粘贴截图。

## 三、状态机与关键算法

### 3.1 工作项状态流转

工作流按工作项大类拆成三套（V31 起，`workflow.applies_to` = TASK / REQUIREMENT / BUG，每类一条 `is_default` 模板）：

```text
缺陷 BUG：待确认 → 处理中 → 已修复 → 已关闭
          另含 再次打开 / 暂不修复，共 6 节点 10 条边（"提交修复""验证通过""修复不通过"等缺陷语义）
任务 TASK：待办 → 进行中 → 已完成 / 已取消（4 节点 6 条边）
需求 REQ ：待处理 / 设计中 / 开发中 / 测试中 四个活跃阶段任意互转，测试通过 → 已完成，已完成可打回 设计中/开发中/测试中（不能回待处理、不能取消），任一活跃阶段 → 已取消，已取消 → 待处理重新打开（6 节点 21 条边）
```

- 合法边一律查 `workflow_transition` 白名单；反向、跳级、跨类别一律非法，返回 400。
- 状态字典 `issue_status` 仍是全局表，但节点归属由各自工作流决定：`GET /statuses?category=` 与 `GET /transitions?category=` 只返回该类别的子集，看板列、详情下拉、新建默认状态一律以此为源。
- 创建/改状态都校验「目标状态属于本类别工作流节点」，避免建出「任务停在已修复」这类跨流程数据。
- 三条改状态路径：`PUT /issues/{id}`（带 statusId）、`PATCH /issues/{id}/position`（拖拽，任务/需求/缺陷三类看板共用）、缺陷列表行内下拉。
- 同事务内必须：校验流转 → 更新 `status_id` → 重算 `sort_key` → 写 `STATUS_CHANGED` 活动。

### 3.2 sort_key（类 LexoRank）

- 取目标列 `beforeId`/`afterId` 的 key，`SortKeyUtils.between(before, after)`；列尾用 `after(tail)`。
- 收益：拖拽只 UPDATE 一行，不做整列 1..N 重排。
- 排序：`ORDER BY sort_key, created_at DESC`。
- 已知限制：跨类型内存合并查询时深页排序不完整，彻底修复需 `UNION ALL` 下推。

### 3.3 编号与 WIP

- `issue_number` 由数据库全局序列生成，三表共用 → 同项目内按创建顺序递增，不按类型分段。
- `board_column.wip_limit` 字段存在，`BoardService` 只读入 `BoardColumnView`，**拖拽时无任何校验或警告**（文档一期"warning"、二期"硬拦截"均未实现）。

## 七、差距清单与建议补齐顺序

| 优先级 | 事项 | 理由 |
|---|---|---|
| 高 | 需求/任务页补状态、优先级、迭代、标签筛选 | 后端 `IssueFilterRequest` 已支持，仅缺 UI，投入最小收益最大 |
| 高 | 后端强制 `category`（缺失返回 400） | 分表隔离文档的核心防串机制缺失，未知 typeCode 还会静默落 task |
| 中 | 工作项导出（复用 `issue:export`） | 权限码已预留，管理场景刚需 |
| 中 | 归档语义文档化（能否反归档、与删除边界） | 前后端各自约定，文档空白 |
| 中 | WIP 限制 | 字段就绪，可分"警告 → 拦截"两步 |
| 低 | Backlog 页、项目级工作流模板 | 需新数据模型，改动大 |
| 低 | 全局搜索、通知、自定义字段、自动化 | 文档明确排在后期 |

> 维护建议：`api.md`/`异常.md`/`数据库.md` 与实现偏差最大，改动接口或表结构时同步刷新，避免文档继续作"伪事实源"。
