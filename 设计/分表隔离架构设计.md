# 缺陷 / 需求 / 任务 物理分表隔离 — 目标架构设计

> 目的：将现有单表 `issue`（靠 `issue_type` 软区分）拆分为三张独立物理表 `task` / `requirement` / `bug`，
> 从存储层彻底隔离三类数据，根治"任务列表出现缺陷数据"的问题；同时保留抽象基类 + 共用 Service 以复用代码。
> 本文档为任务 1（架构设计）产出，是任务 2~7（迁移、实体、Service、Controller、前端、验证）的实施依据。

---

## 一、整体分层架构

```
                         AbstractWorkItem  (抽象基类：三表通用字段 + 审计字段)
                         /          |           \
              Task               Requirement              Bug
           (表 task)          (表 requirement)        (表 bug)
                         \
                BaseWorkItemService<T extends AbstractWorkItem>
                （共用：create/get/update/move/delete/listByFilter/toVO/活动/标签/参与者/抄送/附件/关联）
                         /          |           \
          TaskService        RequirementService        BugService
          （仅注入 TaskMapper）  （仅注入 RequirementMapper）  （仅注入 BugMapper）

        IssueController  →  路由分发（按 category 或拆三路由）→ 对应 *Service
        BoardService / IssueLinkService / ExcelImportService / 权限拦截器  →  按 category 路由
```

**隔离保证**：`task` 表的查询 SQL 永远只扫 `task` 表，物理上不可能返回 `bug` 行；列表/看板接口强制绑定 category。

## 二、实体层设计（共用继承）

### 2.1 抽象基类 `AbstractWorkItem`

包：`com.seven7m.kanban.entity.workitem`

```java
@Getter @Setter
public abstract class AbstractWorkItem extends BaseEntity {
    @TableId(type = IdType.ASSIGN_UUID)
    private UUID id;

    private UUID projectId;
    private String itemNumber;   // 原 issue.issue_number（项目内序号）
    private UUID parentId;       // 父子关系，仅同表内（task→task）
    private UUID issueTypeId;    // 仍保留，指向 issue_type 细分（如缺陷 BUG/FUNC_DEFECT…）
    private UUID statusId;
    private String title;
    private String description;
    private String priority;     // P0~P3
    private UUID reporterId;
    private UUID assigneeId;
    private UUID verifierId;     // 验收人（任务/缺陷用）
    private UUID sprintId;
    private BigDecimal estimate;
    private LocalDate dueDate;
    private String sortKey;
    private Boolean archived;

    /** 子类返回真实表名对应的 category 常量，供路由/子表查询使用 */
    public abstract ItemCategory category();
}
```

> 注：`BaseEntity` 已提供 `createdAt/updatedAt/createdBy/updatedBy`，子类无需重复。

### 2.2 三张实体（各自加专属字段）

```java
@TableName("task")
public class Task extends AbstractWorkItem {
    private String iteration;   // 任务迭代（原 issue.iteration）
    @Override public ItemCategory category() { return ItemCategory.TASK; }
}

@TableName("requirement")
public class Requirement extends AbstractWorkItem {
    private String module;                // 需求归属模块
    private String acceptanceCriteria;    // 验收标准（原 issue.description 之外独立）
    @Override public ItemCategory category() { return ItemCategory.REQUIREMENT; }
}

@TableName("bug")
public class Bug extends AbstractWorkItem {
    private String severity;       // 严重程度
    private String module;
    private String fixVersion;     // 修复版本
    private String source;         // 缺陷来源
    private String iteration;
    private LocalDate planStart;
    private String noFixReason;    // 不修复理由
    @Override public ItemCategory category() { return ItemCategory.BUG; }
}
```

> 字段来源对照（来自 `Issue.java` 与 `IssueVO.java`）：
> - 通用：`project_id, issue_number→item_number, parent_id, issue_type_id, status_id, title, description, priority, reporter_id, assignee_id, verifier_id, sprint_id, estimate, due_date, sort_key, archived`
> - `task`：`iteration`
> - `requirement`：`module` + 新增 `acceptance_criteria`
> - `bug`：`severity, module, fix_version, source, iteration, plan_start, no_fix_reason`
> - 审计字段由 `BaseEntity` 继承，物理表仍含 `created_at/updated_at/created_by/updated_by`

### 2.3 枚举 `ItemCategory`

```java
public enum ItemCategory { TASK, REQUIREMENT, BUG }
```

用于路由分发、子表 `category` 列取值、前端维度。

## 四、子表归属策略（关键隔离点）

子表当前均以 `issue_id` 关联主表：`issue_comment` / `attachment` / `issue_cc` / `issue_participant` / `issue_activity` / `issue_relation` / `issue_label` / `label` / `project_label`。

**采用方案：子表加 `category` 列（最小改动，隔离有效）**

- 为每个子表增加 `category VARCHAR(16) NOT NULL`（取值 `TASK/REQUIREMENT/BUG`）。
- 所有子表读写**强制带 `category` 过滤**，例如任务评论查询：
  ```sql
  SELECT * FROM issue_comment WHERE issue_id = ? AND category = 'TASK';
  ```
- 迁移时按主表归属回填 `category`：
  ```sql
  UPDATE issue_comment c SET category = 'TASK'
    FROM task t WHERE c.issue_id = t.id;
  UPDATE issue_comment c SET category = 'BUG'
    FROM bug b WHERE c.issue_id = b.id;
  UPDATE issue_comment c SET category = 'REQUIREMENT'
    FROM requirement r WHERE c.issue_id = r.id;
  ```
- `issue_relation`（关联）：跨 category 关联**禁止**（task 不能 link 到 bug）。在 `IssueLinkService` 中校验两端 category 一致。
- `issue_label` / `label` / `project_label`：`label` 为全局标签库，`issue_label` 同样加 `category` 隔离。
- `issue_activity`：活动流按 `category` 隔离，保证任务的活动不串到缺陷。

> 备选（未采用）：把子表彻底拆成 `*_task`/`*_bug`/`*_requirement` 三套。隔离更彻底但子表数量翻倍、改动面更大，故采用 `category` 列方案。

## 五、共用抽象 Service 设计（保留共用方法）

### 5.1 `BaseWorkItemService<T extends AbstractWorkItem>`

包：`com.seven7m.kanban.service.workitem`

抽象方法由子类提供表特异性：
```java
protected abstract BaseMapper<T> mapper();
protected abstract ItemCategory category();
```

复用并泛型化的方法（源自现有 `IssueService` 634 行）：
- `create(CreateRequest)` / `getById(UUID)` / `update(...)` / `move(...)` / `delete(UUID)`
- `listByFilter(FilterRequest)` —— **强制 category 过滤**（不再"碰巧传 type"）
- `toVO(T)` / `toVOList` —— 组装 issueType / status / 人员名 / 标签 / 参与者 / 抄送 / 评论数
- 标签增删（`issue_label` + `category`）、参与者/抄送增删、附件列表、活动记录、关联关系

### 5.2 三个薄子类

```java
    @Override protected BaseMapper<Task> mapper() { return taskMapper; }
    @Override protected ItemCategory category() { return ItemCategory.TASK; }

```

### 5.3 路由分发

- `IssueController` 改为：
  - 方案 A（单入口）：`POST /api/issues/filter` 必须带 `category` 参数 → 路由到对应 Service；缺省返回 400。
  - 方案 B（拆路由，更清晰）：`/api/tasks`、`/api/requirements`、`/api/bugs` 三个 Controller 各自注入对应 Service。
- `BoardService.getBoardGrouped`：签名增加 `ItemCategory`，从后端聚合即按表隔离。
- `IssueLinkService`：按 category 路由 Mapper，禁止跨 category 关联。
- `ExcelImportService`：按 sheet 的"类别"列路由到 TaskService/BugService/RequirementService 创建（目前全部走 IssueService.create）。
- 权限拦截器 `ProjectPermissionInterceptor`：按 category 解析工作项所属表再校验权限。
