# 研发项目管理看板系统技术设计文档

版本：V1.0
状态：设计阶段
后端：Java 21 + Spring Boot 3.5
前端：Vue 3 + TypeScript
数据库：PostgreSQL 17
缓存：Redis 8

## 1. 项目定位

本系统用于研发团队进行项目、需求、任务、Bug、Sprint 以及研发流程管理。

核心目标不是完整复制 Jira，而是提供：

```text
项目管理
    ↓
Issue / Task 管理
    ↓
Kanban 看板
    ↓
Workflow 工作流
    ↓
Sprint / Cycle
    ↓
研发数据统计
```

核心体验参考：

* Jira：Issue、Workflow、Sprint、Backlog
* Linear：交互、Board、Filter、Command、Issue Detail
* Trello：简单直观的 Kanban
* GitHub Projects：Issue + Board + Table

第一版本重点解决：

> “一个研发团队能够快速创建任务、分配任务、拖动任务推进状态，并能够清楚看到项目当前进展。”

不追求第一版实现 Jira 的全部功能。

# 6. 为什么不做微服务

这个系统当前最大的问题不是性能。

而是领域模型。

如果一开始拆成：

```text
project-service
issue-service
board-service
workflow-service
sprint-service
user-service
```

会产生大量：

```text
RPC
事务
数据同步
消息
权限
部署
调试
```

但实际业务量完全没有必要。

第一版：

```text
Spring Boot Monolith
```

就足够。

以后如果规模真的达到：

```text
百万级 Issue
大量团队
高频 Activity
复杂通知
大量 Automation
```

再拆。

# 13. Workflow

Workflow 定义：

> Issue 可以如何从一个状态进入另一个状态。

```text

 │
 ▼
IN_PROGRESS
 │
 ▼
CODE_REVIEW
 │
 ▼
TESTING
 │
 ▼
DONE
```

Workflow Transition：

```text
TODO
 ↓
IN_PROGRESS
```

允许。

但是：

```text

 ↓
TODO
```

可能不允许。

因此需要：


# 17. Issue 排序

不要使用：

```text

```

```text

```

```text

b
```

```text

    ├── mapper
    └── db
```

这里我建议采用**领域模块化单体**，而不是传统的：

```text
controller
service
mapper
entity
```

全部混在一起。

例如：

```text
issue/
├── controller
├── service
├── repository
├── entity
├── dto
└── converter
```

这样以后拆服务也比较容易。
