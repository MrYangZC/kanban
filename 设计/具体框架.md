# 二、为什么第一版不做微服务

这个项目目前业务边界非常明确：

```text
用户
  ↓
Workspace
  ↓
Project
  ↓
Issue
  ↓
Board
```

全部围绕 Project / Issue。

如果现在拆：

```text
user-service
project-service
issue-service
workflow-service
board-service
```

马上就会产生：

```text
RPC
服务发现
配置中心
分布式事务
链路追踪
服务间鉴权
部署复杂度
```

但实际上业务量根本不需要这些。

所以第一版：

```text
一个 Spring Boot
一个 PostgreSQL
一个 Redis
一个 MinIO
```

足够。

以后如果 Issue 服务真的成为性能瓶颈，再拆。

# 六、统一返回结构

不要让每个接口自己定义：

```json
{
  "code": 200,
  "msg": "success",
  "data": {}
}
```

建议：

```java
@Data
@AllArgsConstructor
@NoArgsConstructor
public class ApiResponse<T> {

    private int code;

    private String message;

    private T data;

    public static <T> ApiResponse<T> success(T data) {
        return new ApiResponse<>(0, "success", data);
    }

    public static ApiResponse<Void> success() {
        return new ApiResponse<>(0, "success", null);
    }

    public static <T> ApiResponse<T> error(
            int code,
            String message) {

        return new ApiResponse<>(code, message, null);
    }
}
```

成功：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

错误：

```json
{
  "code": 40001,
  "message": "Issue status transition is not allowed",
  "data": null
}
```

# 七、异常体系

建议：

```text
BusinessException
    │
    ├── ResourceNotFoundException
    ├── PermissionDeniedException
    ├── InvalidOperationException
    └── ConflictException
```

例如：

```java
public class BusinessException extends RuntimeException {

    private final int code;

    public BusinessException(int code, String message) {
        super(message);
        this.code = code;
    }
}
```

全局：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public ApiResponse<Void> handleBusiness(
            BusinessException e) {

        return ApiResponse.error(
                e.getCode(),
                e.getMessage()
        );
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ApiResponse<Void> handleValidation(
            MethodArgumentNotValidException e) {

        return ApiResponse.error(
                40000,
                "Request parameter validation failed"
        );
    }

    @ExceptionHandler(Exception.class)
    public ApiResponse<Void> handleException(Exception e) {

        return ApiResponse.error(
                50000,
                "Internal server error"
        );
    }
}
```

生产环境不要直接返回：

```text
e.getMessage()
stacktrace
SQL
```

# 十、Issue 查询

Issue 列表最终可能支持：

```text
关键词
Issue Type
Status
Priority
Assignee
Reporter
Sprint
Label
创建时间
Due Date
```

所以：

```java
@Data
public class IssueQueryRequest {

    private String keyword;

    private UUID issueTypeId;

    private UUID statusId;

    private String priority;

    private UUID assigneeId;

    private UUID reporterId;

    private UUID sprintId;

    private List<UUID> labelIds;

    private Integer page = 1;

    private Integer size = 20;
}
```

SQL 不建议全部交给 Lambda Wrapper。

复杂查询：

```text
issueMapper.xml
```

例如：

```xml
<select id="selectIssuePage"
        resultType="com.xxx.pm.issue.vo.IssueVO">

    SELECT
        i.id,
        i.project_id,
        i.issue_number,
        i.title,
        i.description,
        i.priority,
        i.status_id,
        i.assignee_id,
        i.sprint_id,
        i.created_at
    FROM pm.issue i
    WHERE i.project_id = #{projectId}
      AND i.deleted_at IS NULL

    <if test="query.keyword != null
              and query.keyword != ''">

        AND (
            i.title ILIKE CONCAT('%', #{query.keyword}, '%')
            OR CAST(i.issue_number AS TEXT)
               ILIKE CONCAT('%', #{query.keyword}, '%')
        )

    </if>

    <if test="query.statusId != null">

        AND i.status_id = #{query.statusId}

    </if>

    <if test="query.assigneeId != null">

        AND i.assignee_id = #{query.assigneeId}

    </if>

    ORDER BY i.sort_key, i.created_at DESC

</select>
```

复杂 SQL XML 会比巨型 Wrapper 更容易维护。

# 十一、最关键：Issue 排序

看板拖拽不能每次都：

```text
UPDATE
1
UPDATE
2
UPDATE
3
UPDATE
4
```

否则 Issue 一多就麻烦。

建议使用：

```text
sort_key
```

例如：

```text
A
B
C
D
```

现在：

```text
A
B
C
D
```

把 D 拖到 B 和 C 中间：

```text
A
B
B.5
C
```

实际上可以使用 LexoRank 类似的字符串排序算法：

```text
A
M
Z
```

插入中间：

```text
A
G
M
Z
```

再插：

```text
A
G
J
M
Z
```

这样一次拖拽：

```sql
UPDATE issue
SET sort_key = ?
WHERE id = ?
```

就够了。

这个设计对 Jira/Linear 类型看板非常重要。

# 十四、Workflow 校验

这里千万不要让前端控制状态流转。

```http

```


```text
TODO → DONE
```

是否允许。

```text
workflow_transition
```

```text
throw InvalidOperationException
```

返回：

```json
{
  "code": 40901,
  "message": "Issue cannot transition from TODO to DONE"

```

# 十五、事务边界

例如：

```java

    // 1
    updateIssueStatus();

    // 2
    updateSortKey();

    // 3
```



# 二十、审计字段统一

所有业务表统一：


如果需要：


例如：

```java
@Component
public class AuditMetaObjectHandler
        implements MetaObjectHandler {

    @Override
    public void insertFill(MetaObject metaObject) {

        OffsetDateTime now = OffsetDateTime.now();

        strictInsertFill(
                metaObject,
                "createdAt",
                OffsetDateTime.class,
                now
        );

        strictInsertFill(
                metaObject,
                "updatedAt",
                OffsetDateTime.class,
                now
        );
    }

    @Override
    public void updateFill(MetaObject metaObject) {

        strictUpdateFill(
                metaObject,
                "updatedAt",
                OffsetDateTime.class,
                OffsetDateTime.now()
        );
    }
}
```

# 二十七、Dashboard 才是你最开始说的“看板”

这里要区分两个概念。


```text

```

两种东西。

