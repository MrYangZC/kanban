异常处理规范
本文档基于 yushun-cloud 项目实际实现整理，描述后端统一异常处理与前端响应判定的约定。 涉及源码：yushun-common-core（R、BaseException、ServiceException）、yushun-boot-starter-web（GlobalExceptionHandler）、yushun-boot-starter-satoken（SaTokenExceptionHandler）、yushun-gateway（GatewayExceptionHandler）、plus-ui/src/utils/request.ts。

一、总体原则
所有 HTTP 接口统一以 R<T> 作为响应结构，字段为 code / msg / data。
后端通过全局异常处理器将参数异常、业务异常及系统异常统一转换为标准 R<T> 响应，避免异常信息/堆栈直接暴露给前端。
前端不解析后端异常类型或堆栈，仅依据响应体中的 code 判定请求结果并提示用户。
code 复用 HTTP 语义码（200 成功、400 参数、401 未认证、403 无权限、404/405 路由、500 系统），不另设纯业务错误码段；未知异常的详细堆栈仅记录服务端日志。
二、统一响应结构 R<T>
位于 com.seven7m.common.core.domain.R：

成员	类型	说明
code	int	状态码，成功为 200，其余复用 HTTP 语义
msg	String	提示信息
data	T	业务数据，失败时为 null
常量与工厂方法：

类别	方法 / 常量	说明
常量	SUCCESS = 200	成功状态码
常量	FAIL = 500	失败默认状态码
常量	HttpStatus.WARN	"警告"第三态状态码
成功	R.ok() / R.ok(data) / R.ok(msg) / R.ok(msg, data)	返回成功响应，code=200
失败	R.fail() / R.fail(msg) / R.fail(code, msg) / R.fail(msg, data)	返回失败响应，code 默认 500
警告	R.warn(msg) / R.warn(msg, data)	返回警告响应，code=WARN
判定	R.isSuccess(R) / R.isError(R)	依据 code 是否为 200 判断
三、异常分类与 code 映射
分类	典型异常	处理位置	返回 code	说明
参数异常	MethodArgumentNotValidException、BindException、ConstraintViolationException、HandlerMethodValidationException	GlobalExceptionHandler	500	拼接校验 message，R.fail(message)
参数格式异常	HttpMessageNotReadableException、JsonParseException	GlobalExceptionHandler	400	请求体/JSON 格式非法，R.fail(400, "...")
业务异常	ServiceException、BaseException	GlobalExceptionHandler	异常自带 / 500	业务规则校验失败；ServiceException 带 code 时用其 code，否则回落 500
认证异常	NotLoginException（SaToken）	SaTokenExceptionHandler	401	R.fail(401, "认证失败，无法访问系统资源")
权限异常	NotPermissionException、NotRoleException（SaToken）	SaTokenExceptionHandler	403	R.fail(403, "没有访问权限，请联系管理员授权")
路由异常	NoHandlerFoundException	GlobalExceptionHandler	404	请求地址不存在，R.fail(404, ...)
请求方式异常	HttpRequestMethodNotSupportedException	GlobalExceptionHandler	405	不支持的请求方式，R.fail(405, ...)
系统异常	RuntimeException、Exception、ServletException	GlobalExceptionHandler	500	数据库/网络/未知异常，返回 R.fail("系统内部错误，请稍后重试")；堆栈仅记日志
SSE 认证异常	SseException	GlobalExceptionHandler	401	返回 JSON 字符串 R.fail(401, ...)，且 HTTP 层真实返回 401（@ResponseStatus）
四、处理链路

Controller
    ↓
Service
    ↓
ServiceException / BaseException / 参数异常 / 系统异常
    ↓
GlobalExceptionHandler（及 SaToken / 各 starter 专项 Handler）
    ↓
R<T>
ServiceException 支持占位符 {} 格式化 message，并保留 detailMessage 供内部调试（不外露）。
BaseException 支持 module / code / args，message 优先从国际化资源解析。
五、前端判定规则
位于 plus-ui/src/utils/request.ts 响应拦截器：


const code = res.data.code || HttpStatus.SUCCESS;
if (code === 401) {
  // 登录过期，引导重新登录
} else if (code === HttpStatus.SERVER_ERROR) {
  // 500：error 提示
} else if (code === HttpStatus.WARN) {
  // 警告态：warning 提示
} else if (code !== HttpStatus.SUCCESS) {
  // 其余非 200：error 通知
} else {
  // 成功：resolve(res.data)
}
前端仅依赖 res.data.code 分支处理，不解析异常类型。

六、网关差异
yushun-gateway 的 GatewayExceptionHandler 为 WebFlux 环境，统一向响应体写入 msg（服务未找到 / 内部服务器错误 等），不封装为 R<T>；前端由 errorCode 兜底提示。

七、规范一句话
后端统一以 R<T> 响应，前端仅依据 code 判定结果；业务异常抛 ServiceException，系统异常详情仅记日志不暴露。状态码与错误信息对照：

code	错误信息	触发场景
200	操作成功	请求正常处理完成
400	请求数据格式错误（JSON 解析失败） / 请求参数格式错误	参数格式非法、JSON 解析失败
401	认证失败，无法访问系统资源	未登录 / SSE 认证失败
403	没有访问权限，请联系管理员授权	无权限码 / 无角色权限
404	请求地址不存在	路由未找到
405	请求方式不支持	请求方法不匹配
500	系统内部错误，请稍后重试 / 操作失败	业务异常回落、系统/未知异常、参数校验失败
400	不允许从「{当前状态}」流转到「{目标状态}」	工作流无该流转边（含反向、跳级）
400	状态不属于该工作项类型的工作流	创建/改状态时传入其他类别（任务/需求/缺陷）工作流的 `statusId`
