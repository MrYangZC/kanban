## 1. 先确定核心领域模型

系统采用：

```text
Workspace
    │
    ├── User / Member
    │
    └── Project
          │
          ├── Issue
          │     ├── Comment
          │     ├── Attachment
          │     ├── Activity
          │     ├── Label
          │     └── Relation
          │
          ├── Board
          │     └── BoardColumn
          │
          ├── Workflow
          │     ├── WorkflowStatus
          │     └── WorkflowTransition
          │
          └── Sprint
```

最核心的关系是：

```text
Issue
 │
 ├── Status ────────── WorkflowStatus
 │
 ├── Sprint
 │
 └── Project
          │
          ├── Board
          │      └── BoardColumn
          │               │
          │               └── Status
          │
          └── Workflow
```

这里有一个设计原则：

> **Issue 的状态属于 Workflow，Board 只是把这些状态展示成列。**

所以不要在 `issue` 表里保存 `board_column_id`。

# 11. Workflow Status

Workflow 与 Status 的关联：

```sql
CREATE TABLE workflow_status (
    id UUID PRIMARY KEY,

    workflow_id UUID NOT NULL,

    status_id UUID NOT NULL,

    sort_order INTEGER NOT NULL DEFAULT 0,

    CONSTRAINT uk_workflow_status
        UNIQUE (workflow_id, status_id)
);
```

这里我要修正一下上一版设计：**如果我们正式采用 Workflow 独立配置，`status` 最好拆成全局/项目级 Status + Workflow 映射。**

因此最终模型应该是：

```text
Project
   │
   ├── Status
   │
   └── Workflow
          │
          └── WorkflowStatus
                  │
                  └── Status
```

而不是让 `workflow_status` 自己同时承担 Status 实体。

这样以后可以：

```text
Workflow A
TODO → DEVELOPING → TESTING → DONE

Workflow B
需求 → 设计 → 开发 → 验收 → 发布
```

# 14. 为什么 Issue 不保存 Board ID

假设：

```text
Issue YSP-102

Status = DEVELOPING
```

Board A：

```text
待处理
开发中
测试中
完成
```

它显示：

```text
开发中
```

但是另一个 Board：

```text
需求
设计
开发
验收
发布
```

也可以把：

```text
DEVELOPING
```

映射到：

```text
开发
```

所以：

```text
Issue
  ↓
Status
  ↓
Board Column
```

而不是：

```text
Issue
  ↓
Board Column
```

这个设计会让你的系统后期扩展能力强很多。

# 24. Board 查询

打开看板：

```text
GET /api/v1/projects/{projectId}/board
```

后端核心查询实际上就是：

```sql
SELECT *
FROM issue
WHERE project_id = ?
  AND deleted_at IS NULL
ORDER BY status_id, sort_key;
```

然后根据：

```text
board_column
```

分组。

这里不要为每一列查询一次数据库。

错误：

```text
TODO      → SQL
DEV       → SQL
TEST      → SQL
DONE      → SQL
```

正确：

```text
一次 SQL
    ↓
全部 Issue
    ↓
Java 分组
```

# 25. MyBatis-Plus 的定位

# 26. MyBatis-Plus 不要滥用

简单查询：

```java
issueMapper.selectById(id);
```

可以。

复杂 Board 查询：

```java
issueMapper.selectBoardIssues(projectId);
```

直接写 XML / SQL。

不要为了 MyBatis-Plus Wrapper 而 Wrapper。

例如这种：

```java
lambdaQuery()
    .eq(...)
    .and(...)
    .or(...)
    .nested(...)
    .orderBy(...)
```

复杂之后反而难维护。

**MyBatis-Plus 是 ORM/CRUD 工具，不是让所有 SQL 都必须 Wrapper 化。**
