## 二、总体结论

**一句话结论：约束与索引体系齐全、主外键与唯一约束基本覆盖到位，但存在「每项目副本式冗余」为主、以「角色关联口径不一致」「菜单与权限职责重叠」「数据异常」为辅的四类结构性问题。**

分维度评价：

| 维度 | 评价 | 等级 |
|------|------|------|
| 主键/唯一约束 | 每张表均有主键，核心业务唯一性（project_key、issue_number、状态/类型 code）均有 UK 约束 | 良好 |
| 索引覆盖 | issue 表 12 个索引（项目/状态/负责人/里程碑等），查询路径覆盖较全 | 良好 |
| 外键完整性 | 外键较全，但几乎全部 `ON DELETE NO ACTION`，删除成本高 | 一般 |
| 数据冗余 | issue_status/issue_type/label/workflow 等按项目复制，冗余度高 | 较差 |
| 关联口径一致性 | 角色关联同时存在 uuid/code/project 三套口径 | 较差 |
| 数据质量 | 存在乱码、类型混用、占位 UUID 硬编码 | 较差 |

## 三、分级问题清单

### 3.1 P0 级（架构性问题，建议优先整改）

#### P0-1：状态/类型/工作流「每项目副本」导致的高冗余与全局一致性风险

**问题描述**：`issue_status`、`issue_type`、`workflow`、`workflow_status`、`workflow_transition`、`label`、`board_column` 均以 `project_id` 作为维度之一，将「本应全局共享的字典/工作流定义」复制到每个项目下。

**现状证据**：

- `issue_status`：表含 `project_id`，每个项目复制 6 条相同状态（`TO_CONFIRM / REOPENED / IN_PROGRESS / FIXED / WONT_FIX / CLOSED`），唯一约束为 `uk_issue_status UNIQUE("project_id", "code")`（`public.sql` 行 4973）。
- `issue_type`：表含 `project_id`，每个项目复制 10 条类型（`TASK / BUG / STORY / FEATURE / IMPROVEMENT / FUNC_DEFECT / PERF_DEFECT / SEC_DEFECT / COMPAT_DEFECT / UI_DEFECT`），唯一约束 `uk_issue_type UNIQUE("project_id", "code")`（行 4983）。
- `workflow`：每个项目一条 `缺陷工作流`，且用部分唯一索引 `uk_workflow_default_per_project UNIQUE ... WHERE is_default = true`（行 5163）保证「每项目仅一条默认工作流」——这本身就是「每项目一份」设计的外显。
- `workflow_status`：每个 workflow 复制 6 条状态节点（行 4380 起）；`workflow_transition`：每个 workflow 复制 10 条迁移边（行 4552 起），`from_status_id / to_status_id` 直接引用 `issue_status`（外键段行 5333–5335）。
- `label`：`project_id + name`，唯一约束 `uk_label UNIQUE("project_id", "name")`（行 4993）。
- `board` / `board_column`：同样携带 `project_id`（行 77 / 122 起）。

**影响**：

1. 数据膨胀：假设 N 个项目，状态/类型/工作流相关表合计每项目约 33 条副本记录（6 状态 + 10 类型 + 1 工作流 + 6 工作流节点 + 10 迁移边），N=10 即约 330 条冗余。
2. 语义漂移：同一 `code` 在不同项目里被允许拥有不同 `name`/`color`/`sort`，无法保证全局一致性；跨项目报表、统计、搜索时同一状态含义不统一。
3. 跨项目迁移不可行：`workflow_transition` 的 `from_status_id/to_status_id` 绑定项目内 `issue_status.id`，导致无法跨项目复用工作流模板。
4. 维护成本：新增一个全局类型/状态需遍历所有项目批量写入，极易漏项。

**修复结果（已落地，V24~V35）**：`issue_status`/`issue_type`/`workflow` 等均已去 `project_id` 全局化；`workflow` 改为模板并由 `project.workflow_id` 引用。当前现状：`issue_status` 全局 16 条（三类工作流共用一张字典表），`workflow` 3 条（`applies_to` = TASK / REQUIREMENT / BUG，各一条 `is_default`），`workflow_status` 16 条（4/6/6），`workflow_transition` 37 条（6/21/10）。上文「每项目复制 6 状态 / 10 边」属评审当时的旧快照。

**建议**：见第四章「架构级重构方案：全局共享模型」。

#### P0-2：角色关联「三轨并存」口径不一致

**问题描述**：RBAC 重构后，角色到权限/菜单/用户的关联同时存在三套关联口径，且主键形态不统一。

**现状证据**：

- `role_menu`：以 `id (uuid)` 为主键，`UNIQUE(role_id, menu_id)`（行 5102），`role_id/menu_id` 为 uuid。
- `role_permission`：以 `(role_code, permission_code)` 为复合主键（行 5115），`code` 关联。
- `user_role`：以 `id (uuid)` 为主键，`UNIQUE(user_id, role_id, project_id)`（行 5153），`role_id` 为 uuid 且额外携带 `project_id`。
- `role`：主键 `id (uuid)`，另有 `uk_role_code UNIQUE(code)`（行 5088）；`permission` 以 `code` 为主键（行 5025）。

**影响**：

1. 同一「角色」概念在不同关联表里分别用 uuid 与 code 表达，`role_permission` 通过 code、`role_menu`/`user_role` 通过 uuid，跨表 join 必须经 `role` 表桥接，且 code 变更时需同步两套。
2. `user_role` 携带 `project_id` 而 `role_menu/role_permission` 不带，导致「项目级角色授权」与「全局角色权限定义」割裂，无法清晰回答「某用户在项目 P 拥有哪些菜单/权限」。
3. 权限模型存在两套真相来源（`menu.type='BUTTON'` 兼任按钮权限 vs `permission` 表），易产生冲突。

**建议**：见 3.2 P1-1 与第四章「统一角色关联口径」。

### 3.2 P1 级（中高风险，建议尽快整改）

#### P1-1：`menu` 与 `permission` 职责重叠

**问题描述**：`menu` 表用 `type` 字段区分 `MENU` 与 `BUTTON`，即以「菜单表」兼任「按钮权限点」；同时系统又单独建了 `permission` 表（主键 code），二者职责重叠。

**现状证据**：

- `menu`：`type` 含 `MENU` 与 `BUTTON`（行 3499 起），`uk_menu_code UNIQUE(code)`（行 5003）。
- `permission`：独立表，主键 `code`（行 5025）。
- `role_menu` 关联 menu（uuid），`role_permission` 关联 permission（code）。

**影响**：

1. 按钮权限有两处定义入口（menu.type=BUTTON 与 permission 表），授权时需同时维护两处，易漏配。
2. 前端/后端鉴权需兼容两套数据源，判断逻辑复杂化。

**建议**：收敛职责——`menu` 只负责导航/菜单树，按钮/操作权限统一由 `permission` 承载；或反之保留一套，废弃另一套。迁移时以 code 为主键对齐，保留映射。

---

#### P1-2：`project_member` 与 `user_role` 并存导致成员口径不一致

**问题描述**：项目成员关系存在两张表，语义重叠但约束口径不同。

**现状证据**：

- `project_member`：`UNIQUE(project_id, user_id)`（行 5060），历史遗留「项目成员」概念。
- `user_role`：`UNIQUE(user_id, role_id, project_id)`（行 5153），重构后承载「用户在项目的角色」。

**影响**：

1. 「谁在项目里」有 `project_member` 与 `user_role` 两个答案，若未同步会不一致。
2. 新人入项目需同时写两张表，漏写导致权限缺失或成员列表缺失。

**建议**：明确 `project_member` 为「成员名册」（是否属于项目），`user_role` 为「成员的角色授权」，建立「成员必先存在于 project_member」的业务约束；或合并为单表（member 含 roles 数组）。

---

#### P1-3：`issue.issue_number` 类型混用（int8 列混入字符串字面量）

**问题描述**：`issue_number` 定义为 `int8`，但导出数据中混入带引号的字符串字面量。

**现状证据**：

- 表定义：`issue_number int8`（行 340），唯一约束 `uk_issue_number UNIQUE("project_id", "issue_number")`（行 4931）。
- 数据段混用：`INSERT ... VALUES (..., '5801', ...)`（带单引号，行 375–377 一带）与 `..., 6717, ...`（纯数字）并存。

**影响**：

1. `issue_number` 作为编号本应统一为数值或字符串，混用会导致排序、比较、跨端类型映射（Java Long vs String）异常。
2. 唯一约束在「字符串 `'5801'`」与「数字 `5801`」可能被视为不同值，破坏编号唯一性。

**建议**：统一为字符串（`varchar`，编号无算术语义）或纯数值；清洗既有数据并重建唯一约束。

---

#### P1-4：软删除模型缺乏「软删除唯一约束」

**问题描述**：多表采用 `deleted`/`archived` int 标记 + 部分索引 `WHERE deleted = 0`，但唯一约束未把 `deleted` 纳入，删除后同 code 无法复用。

**现状证据**：

- 索引段存在多处部分索引，例如 `... WHERE deleted = 0`（行 4832–5101 一带）。
- `issue` 表同时含 `archived` 与 `deleted` 两个标记（行 337 起），语义重叠。
- 唯一约束如 `uk_issue_status(project_id, code)`、`uk_label(project_id, name)` 均未含 `deleted` 维度。

**影响**：

1. 逻辑删除一条记录后，同名/同 code 记录无法重新创建（唯一约束冲突），只能物理删除或改 code。
2. `archived` 与 `deleted` 双标记并存，代码需判断两个字段，易漏判。

**建议**：统一软删除语义（仅保留 `deleted`），唯一约束改为 `(project_id, code, deleted)` 或采用部分唯一索引 `WHERE deleted = 0`，使「活跃记录唯一、已删除可复用」。

### 3.3 P2 级（低风险，建议择机修复）

#### P2-1：`project.name` 存在乱码数据

**问题描述**：导出数据中项目名称出现乱码。

**现状证据**：

- 数据段：`('d2dec760-...', 'P1', '娴嬭瘯椤圭洰', ...)`（行 3634 一带），`娴嬭瘯椤圭洰` 为「测试项目」的 UTF-8 字节被误按 GBK 解码产生的乱码。

**影响**：前端展示乱码，影响用户体验与搜索匹配。

**建议**：定位并修复该条记录，统一编码（UTF-8）重新写入正确名称。

---

#### P2-2：系统占位 UUID 硬编码

**问题描述**：`sys_user` 等表中存在硬编码系统占位 UUID `00000000-0000-0000-0000-000000000001`。

**影响**：魔法值散落于数据/代码，可读性与可维护性差；若未来引入真实 UUID 生成策略易冲突。

**建议**：以常量/配置集中管理系统账号标识，或在建库时以确定性方式生成并文档化。

---

#### P2-3：外键几乎全部 `ON DELETE NO ACTION`

**问题描述**：外键段（行 5206–5336）绝大多数 `ON DELETE NO ACTION`，仅 `project_favorite` 与 `role_permission` 为 `CASCADE`。

**影响**：删除项目/用户等父记录时，必须按依赖顺序手工清理，否则报外键冲突；易产生残留孤儿数据或删除失败。

**建议**：对明确「子随父亡」的关系（如 `issue` → `issue_activity/issue_comment/issue_label/issue_relation`，`workflow` → `workflow_status/workflow_transition`）改为 `CASCADE` 或 `SET NULL`，其余保留 `RESTRICT` 并文档化删除顺序。

---

#### P2-4：`issue.participants` / `issue.cc_users` 用 jsonb 存 uuid 数组

**问题描述**：参与者/抄送人用 `jsonb` 数组存 uuid，而非关联表。

**现状证据**：`issue` 表行 365 `participants jsonb NOT NULL DEFAULT '[]'`、行 366 `cc_users jsonb NOT NULL DEFAULT '[]'`。

**影响**：
1. 无法建立外键约束保证成员真实存在；删除用户无法级联清理，产生悬空引用。
2. 无法高效 join 查询参与者姓名/头像，需应用层反查。
3. 无法按参与者建索引/统计（如「某人参与的任务」），只能 `jsonb` 慢扫。

**建议**：拆为关联表 `issue_participant(issue_id, user_id)`、`issue_cc(issue_id, user_id)`，主键 `(issue_id, user_id)`，外键 `ON DELETE CASCADE`。

---

#### P2-5：`issue.sort_key` 用 varchar

**问题描述**：看板拖拽排序键使用 `varchar(64)`。

**现状证据**：`issue` 表行 353 `sort_key varchar(64) NOT NULL`。

**影响**：`varchar` 承载 lexorank/fractional 排序键本身合理，但 64 长度在深插场景（反复在同一区间插入）会不断加长、最终溢出；且其排序语义与 `board_column.sort_order` 存在重叠，职责不清。

**建议**：确认排序策略——若为 lexorank 深插，扩为 `varchar(255)` 并定期重排；若仅看板列内排序，明确语义并收敛到 `board_column`，避免双轨。

---

#### P2-6：多数表 `id` 无默认值，依赖应用层生成 UUID

**问题描述**：主键 `id` 几乎全部无数据库默认值。

**现状证据**：全库仅 `risk.id` 有 `DEFAULT gen_random_uuid()`（行 3819），其余 28 张表 `id uuid NOT NULL` 均无默认值。

**影响**：应用层（MyBatis-Plus `ASSIGN_UUID`）是唯一生成方，一旦出现旁路写入（Flyway 种子数据、手工 SQL、脚本导入、跨服务直连）且未显式传 id，即触发非空约束报错；不符合「数据库可自治」的最佳实践。

**建议**：统一 `ALTER TABLE ... ALTER COLUMN id SET DEFAULT gen_random_uuid();`，与应用层 `ASSIGN_UUID` 兼容（显式传 id 用应用层，未传用 DB）。

## 四、架构级重构方案：全局共享模型

> 本章为「建议」，不落地。目标是消除 3.1 P0-1 的每项目冗余，将字典/工作流由「每项目副本」改为「全局共享 + 项目级配置」。

### 4.1 目标模型

| 现状（每项目副本） | 目标（全局共享） |
|--------------------|------------------|
| `issue_status(project_id, code, ...)` | `issue_status(id, code, name, color, sort, ...)`，**去除 project_id**，code 全局唯一 |
| `issue_type(project_id, code, ...)` | `issue_type(id, code, name, ...)`，**去除 project_id**，code 全局唯一 |
| `label(project_id, name, ...)` | 拆为 `label(id, name, ...)` 全局 + `project_label(project_id, label_id)` 关联 |
| `workflow(project_id, name, is_default)` | `workflow(id, name, ...)` 全局模板 |
| `workflow_status(workflow_id, status_id)` | 关联全局 `issue_status`，status_id 引用全局 status |
| `workflow_transition(workflow_id, from/to_status_id)` | 同上，迁移边引用全局 status |
| `board(project_id, ...)` / `board_column(...)` | `board` 保留 project 维度（看板属于项目），`board_column` 若为通用列定义可全局化；若列绑定项目工作流则改为「项目看板 → 列」映射 |

**核心原则**：

1. **字典类**（状态/类型/标签）——全局唯一，项目通过「选用/可见性」关联，而非复制。
2. **工作流类**——工作流本身为可复用模板，项目通过 `project.workflow_id` 引用，而非每项目一份。
3. **看板类**——`board` 属于项目（保留 project_id），`board_column` 引用「全局列定义 + 项目工作流映射」。

### 4.2 去冗余方式

1. **状态/类型**：`issue` 表直接引用全局 `issue_status.id` / `issue_type.id`，删除每项目副本。
2. **标签**：`label` 全局去重，`issue_label` 关联 `issue_id ↔ label_id`，`project_label` 控制项目可选标签集合。
3. **工作流**：`workflow` 成为独立模板，`project.workflow_id` 外键引用；`workflow_status/workflow_transition` 引用全局 status，支持多项目共享同一工作流模板。
4. **兼容过渡**：可保留 `project_id` 为「项目级覆盖（override）」字段，值为 NULL 表示继承全局默认，非 NULL 表示项目自定义覆盖——即「全局默认 + 项目增量覆盖」混合模型，兼顾一致性与灵活性。

### 4.3 迁移思路

1. **抽公共字典**：将各项目 `issue_status/issue_type` 按 code 去重，生成全局主数据，建立「旧 project_id+id → 新全局 id」映射表。
2. **回填引用**：更新 `issue.status_id/type_id`、`workflow_status.status_id`、`workflow_transition.from/to_status_id` 指向新全局 id。
3. **工作流模板化**：将每项目 `缺陷工作流` 合并为模板，`project.workflow_id` 指向模板。
4. **标签去重**：`label` 按 name 去重，重建 `issue_label` 关联。
5. **删除旧列**：确认无引用后 drop 各表 `project_id` 列，调整唯一约束为全局唯一。
6. **Flyway 新脚本**：在现有 V10 之后新增 V11+ 迁移脚本，保证可回滚、可增量。

### 4.3.2 迁移 SQL（按依赖顺序执行）

```sql
-- ========== 阶段 A：issue_type 全局化 ==========
-- A1. 建全局表（复用旧结构，去掉 project_id）
CREATE TABLE issue_type_g (LIKE issue_type INCLUDING ALL);
ALTER TABLE issue_type_g DROP COLUMN project_id;
ALTER TABLE issue_type_g ADD CONSTRAINT uk_issue_type_g_code UNIQUE (code);

-- A2. 按 code 去重灌全局数据（10 条，name/icon/color/sort_order 全同，任取一行）
INSERT INTO issue_type_g (id, name, code, icon, color, sort_order, created_at)
SELECT DISTINCT ON (code) id, name, code, icon, color, sort_order, created_at
FROM issue_type ORDER BY code, sort_order;

-- A3. 回填 issue.issue_type_id（旧项目内 id -> 全局 id，按 code 映射）
UPDATE issue i
SET issue_type_id = g.id
FROM issue_type o JOIN issue_type_g g ON o.code = g.code
WHERE i.issue_type_id = o.id;

-- A4. 切换表 + 补外键
DROP TABLE issue_type;
ALTER TABLE issue_type_g RENAME TO issue_type;
ALTER TABLE issue ADD CONSTRAINT fk_issue_type
  FOREIGN KEY (issue_type_id) REFERENCES issue_type(id);

-- ========== 阶段 B：issue_status 全局化 ==========
-- 同 A，仅多回填 category 字段，目标唯一约束为 (code)
CREATE TABLE issue_status_g (LIKE issue_status INCLUDING ALL);
ALTER TABLE issue_status_g DROP COLUMN project_id;
ALTER TABLE issue_status_g ADD CONSTRAINT uk_issue_status_g_code UNIQUE (code);
INSERT INTO issue_status_g (id, name, code, category, color, sort_order, created_at, updated_at)
SELECT DISTINCT ON (code) id, name, code, category, color, sort_order, created_at, updated_at
FROM issue_status ORDER BY code, sort_order;
UPDATE issue i
SET status_id = g.id
FROM issue_status o JOIN issue_status_g g ON o.code = g.code
WHERE i.status_id = o.id;
DROP TABLE issue_status;
ALTER TABLE issue_status_g RENAME TO issue_status;

-- ========== 阶段 C：label 全局化 ==========
-- 按 name 去重（label 无 code，以 name 为准）
CREATE TABLE label_g (LIKE label INCLUDING ALL);
ALTER TABLE label_g DROP COLUMN project_id;
ALTER TABLE label_g ADD CONSTRAINT uk_label_g_name UNIQUE (name);
INSERT INTO label_g (id, name, color, created_at)
SELECT DISTINCT ON (name) id, name, color, created_at FROM label ORDER BY name;

-- 回填 issue_label.label_id（旧 id -> 全局 id）
UPDATE issue_label il
SET label_id = g.id
FROM label o JOIN label_g g ON o.name = g.name
WHERE il.label_id = o.id;

-- 生成 project_label（项目 -> 其原有用过的全局标签）
INSERT INTO project_label (project_id, label_id)
SELECT DISTINCT o.project_id, g.id
FROM label o JOIN label_g g ON o.name = g.name;

DROP TABLE label;
ALTER TABLE label_g RENAME TO label;

-- ========== 阶段 D：workflow 模板化 ==========
-- D1. 合并每项目「缺陷工作流」为 1 个全局模板（取第一行为代表）
CREATE TEMP TABLE _map_wf AS
SELECT o.id AS old_id, (SELECT MIN(id) FROM workflow) AS new_id
FROM workflow o;

-- D2. project 绑定模板
UPDATE project p SET workflow_id = m.new_id
FROM _map_wf m WHERE m.old_id = (SELECT w.id FROM workflow w WHERE w.project_id = p.id LIMIT 1);

-- D3. workflow_status.status_id 指向全局 status
UPDATE workflow_status ws
SET status_id = g.id
FROM issue_status o JOIN issue_status_g g ON o.code = g.code
WHERE ws.status_id = o.id;

-- D4. workflow_transition 的 from/to_status_id 指向全局 status（同理）
UPDATE workflow_transition wt
SET from_status_id = g.id
FROM issue_status o JOIN issue_status_g g ON o.code = g.code
WHERE wt.from_status_id = o.id;
UPDATE workflow_transition wt
SET to_status_id = g.id
FROM issue_status o JOIN issue_status_g g ON o.code = g.code
WHERE wt.to_status_id = o.id;

-- D5. 删除每项目冗余 workflow（保留代表模板行），workflow 去 project_id
DELETE FROM workflow WHERE id <> (SELECT MIN(id) FROM workflow);
ALTER TABLE workflow DROP COLUMN project_id;
-- 补外键
ALTER TABLE workflow_status ADD CONSTRAINT fk_ws_workflow
  FOREIGN KEY (workflow_id) REFERENCES workflow(id) ON DELETE CASCADE;
ALTER TABLE workflow_status ADD CONSTRAINT fk_ws_status
  FOREIGN KEY (status_id) REFERENCES issue_status(id);

-- ========== 阶段 E：board_column 去 name ==========
-- 若 board_column.name 完全等于 issue_status.name，则 drop name，join 获取
ALTER TABLE board_column DROP COLUMN name;
```

> 说明：阶段 B/D 中 `issue_status_g` 是阶段 B 的中间表，阶段 D 复用它做旧→新映射；若阶段 B 已 `RENAME` 为 `issue_status`，则 D3/D4 的 `issue_status_g` 应改为 `issue_status`（结合旧表备份表名取用）。落地时以正式 Flyway 脚本为准，此处为逻辑示意。

### 4.5 角色关联口径统一（对应 3.1 P0-2）

**推荐方案：统一用 `role.id`（uuid）做外键**。理由：`user_role`、`role_menu` 已用 uuid，只需改 `role_permission` 一张表；uuid 引用稳定，role 重命名/改 code 不影响关联；`role.code` 保留为业务唯一键（`uk_role_code`）供前端权限码判断。

### 4.6 menu 与 permission 职责收敛（对应 3.2 P1-1）

**方案**：`menu` 只负责导航树（`type` 仅保留 `MENU`/`CATALOG`），按钮/操作权限统一由 `permission` 承载，形成单一权限码体系。

```sql
-- 1. 将 menu.type='BUTTON' 的节点迁移为 permission 记录（code 映射：ISSUE_CREATE -> issue:create）
INSERT INTO permission (code, name)
SELECT 'issue:' || lower(replace(m.code, 'ISSUE_', '')), m.name
FROM menu m WHERE m.type = 'BUTTON';

-- 2. role_menu 中的 BUTTON 授权迁移到 role_permission
INSERT INTO role_permission (role_id, permission_code)
SELECT rm.role_id, p.code
FROM role_menu rm JOIN menu m ON rm.menu_id = m.id JOIN permission p ON p.code = 'issue:' || lower(replace(m.code, 'ISSUE_', ''))
WHERE m.type = 'BUTTON';

-- 3. 清理 menu 中的 BUTTON 节点及其 role_menu 关联
DELETE FROM role_menu WHERE menu_id IN (SELECT id FROM menu WHERE type = 'BUTTON');
DELETE FROM menu WHERE type = 'BUTTON';
```

> 落地需先梳理 `menu.type='BUTTON'` 与 `permission` 的完整映射关系，确保无遗漏后执行。
